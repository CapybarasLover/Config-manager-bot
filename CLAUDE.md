## Build & Run

```powershell
# IntelliJ bundled Maven (not in PATH — always use full path)
$mvn = "C:\Users\andre\AppData\Local\Programs\IntelliJ IDEA\plugins\maven\lib\maven3\bin\mvn.cmd"
& $mvn clean package -DskipTests

# Run locally (dev mode) — env vars must be set first
java -Dapp.env=dev -jar target/Config_bot-2.0-SNAPSHOT.jar

# Run in production
java -Dapp.env=prod -jar target/Config_bot-2.0-SNAPSHOT.jar

# One-off: merge inbounds into the client-centric model (attaches the XHTTP inbound
# to every WS client and the Reality inbound to every bot client, including those who chose a single
# protocol; idempotent; never deletes anything)
java -Dapp.env=prod -cp target/Config_bot-2.0-SNAPSHOT.jar com.petr.tools.MergeInbounds
# optional arg: latv | germ | pol | both (default both = every configured panel)

# Smoke test against a live panel (creates and deletes a test client claudetest_config)
java -Dapp.env=prod -cp target/Config_bot-2.0-SNAPSHOT.jar com.petr.tools.PanelSmokeTest [latv|germ|pol|both]
# List a panel's inbounds (id, port, transport) without changing anything
java -Dapp.env=prod -cp target/Config_bot-2.0-SNAPSHOT.jar com.petr.tools.PanelSmokeTest inbounds [latv|germ|pol]
```

`app.env` (`prod` | `dev`) controls DB connection string and 3x-ui inbound IDs.

## Scenario tests

```bash
bash scripts/run-scenarios.sh
```

Runs every user and admin flow through the real `Bot` (`src/test/java/com/petr/bot/ScenarioRunner.java`). Telegram and all three panels are local fakes (`FakeTelegram`, `FakePanel`, shaped after real v3.8.5 responses), the DB is a throwaway Postgres; `.env`, real panels and Telegram are never touched. Needs a JDK (`JAVA_BIN`), PostgreSQL binaries (`PG_BIN`) and an already built `target/Config_bot-2.0-SNAPSHOT.jar`: Lombok classes are taken from that jar, so rebuild it after changing them. The bot's own output goes to `target/scenarios/bot.log`. Add a scenario for every bug fixed.

## Architecture

```
Bot.java  (telebof: @MessageHandler + @CallbackHandler)
  └── ConfigManager / ConfigManagerImpl
        ├── PanelService → ApiRequests → 3x-ui HTTP API (HTTP/1.1, cookie auth)
        └── DbService → UserDao / ConfigDao → PostgreSQL (Hibernate 7)
```

### Key classes

**`Bot` / `BotHandler`** — All Telegram routing. Uses inline keyboards for all interactions (no plain-text command flows). State machine via `bot.setState` / `bot.clearState`. Two in-memory maps track message IDs for editing:
- `awaitingMessageId: Map<Long, Integer>` — message to edit after user types config name
- `deleteMessageId: Map<Long, Integer>` — admin panel message to edit after typing config name to delete

`adminNotifications` tracks the notification messages of each open request (`"userId:country"` → adminId → messageId), so a decision by one admin updates all of them. It lives in memory: after a restart another admin's message updates only when they press its button (the press is still safe, the decision comes from the DB).

Never rely on in-memory state for a choice the user made earlier: buttons outlive it (restart, another finished request, double tap). The country travels inside callback data (`config_type:both:germ`, `approve:<id>:<country>`). Edit messages through `show(...)` (a repeated identical edit is not an error; falls back to a new message) and answer callbacks through `answer(...)` (an expired query does not abort the handler).

**`TelebofThreadSafety`** — telebof 1.2.3 builds all Bot API requests with one shared `Request.Builder`, so concurrent calls silently overwrite each other (lost and duplicated messages). `Bot.buildClient` replaces it with a per-thread builder and sets 8 handler threads (the default of 2 lets two hung panel calls stop the bot). Always create the client through `buildClient`.

**`isAdmin` filter** — `CustomFilter` that checks `ADMIN_CHATS` env var for both `Message` updates and `CallbackQuery` updates (handles both types). Logs every check.

**Client-centric model (3x-ui ≥ v3.2.5, verified against v3.8.5):** clients are standalone entities under
`/panel/api/clients/*`. One Telegram user → **one client** (one UUID, one email,
one subId) attached to multiple inbounds (WS + XHTTP). The subscription
`/sub/{subId}` then aggregates both protocol links automatically. The old model
(two separate clients per user sharing one subId) is no longer valid — duplicate
subId across different emails is rejected.

**Single implementation, per-panel config.** All panels run the **same** request
and service logic — they differ only by configuration. There is no per-country code
fork anymore:
- **`PanelConfig`** — holds one panel's settings (label, baseUrl, credentials,
  `wsInbound` (nullable → WS disabled), `xhttpInbound` (nullable → XHTTP disabled), `realityInbound` (nullable → Reality disabled), `subBaseUrl`). Factories
  `PanelConfig.latv()` / `germ()` / `pol()` build these from env; `PanelConfig.COUNTRIES` (`latv`, `germ`, `pol`) is the button order and `forCountry(code)` the lookup. `offersTypeChoice()` (WS and XHTTP both present) decides whether the user picks a type; `singleTypes()` gives one button per configured protocol. Otherwise `defaultType()` (`BOTH` — every protocol of the panel) is used without asking, so Riga gives WS + Reality.
- **`ConfigType`** — `WS` / `XHTTP` / `REALITY` attach exactly that protocol, `BOTH` (button «Все», callback `both`, same data as the former «Оба» so old messages keep working) attaches every protocol of the panel. Reality is no longer attached on its own: a user who picks «WebSocket» gets WS only. Attaching never detaches: picking one protocol later keeps the ones a client already has.
  - Latv: WS inbound from `LATV_WS_INBOUND_PROD/DEV` (default prod=`1`/dev=`3`); **no XHTTP** (removed from the Riga server; hard-coded `null`, the user skips the config-type choice); Reality inbound `LATV_REALITY_INBOUND_PROD` (default `8`); sub base from `LATV_SUB_BASE_URL` (default `https://petromerzlikino.site:2096/sub/`).
  - Germ: WS inbound `GERM_WS_INBOUND` (default `3`), XHTTP inbound `GERM_XHTTP_INBOUND` (default `2`), Reality inbound `GERM_REALITY_INBOUND` (default `5`), sub base `GERM_SUB_BASE_URL`.
  - Pol (Warsaw): `pol()` returns `null` without `POL_PANEL_HOME_URL`, and `ConfigManagerImpl` then skips the country (the bot must start without Polish secrets). Inbounds only from `POL_*_INBOUND`, no defaults.
- **`ApiRequestsImpl`** (one class for all panels) — HTTP client (forced HTTP/1.1). Authenticates with the panel **API token** via `Authorization: Bearer <token>` on every request — no login/session/cookies/CSRF (the panel skips CSRF for Bearer-authed, non-browser callers). `executeWithRetry` retries up to 2× on `RequestException`. Requests time out (10 s connect, 20 s request). Client endpoints (`add`/`attach`/`del`/`get`/`links`/`list`) send/receive **JSON** (`application/json`).
- **`PanelServiceImpl`** (one class for all panels) — `createClient(email, tgId, ConfigType)` is **create-or-attach**: no client → create in target inbounds; client exists → attach the missing inbounds, reusing its UUID/subId. A newly added Reality always ends up with XTLS Vision (see "XTLS Vision" in the API notes). Returns `String[]{wsLink, subLink, xhttpLink, realityLink}` (nulls allowed); links are fetched from the panel (`links/{email}`) and classified by matching the link port against each inbound's port (`GET inbounds/get/{id}`), falling back to `type=xhttp`/`splithttp` → xHTTP, `type=ws` → WS, else → Reality. `readClient(email)` returns the current links without changing the panel. `deleteClient(email)` removes the client from all inbounds in one call, together with its old `{base}_xhttp` twin if one exists (otherwise a deleted user keeps a working xHTTP link). Old `_xhttp` clients are never synced into the DB.

**`ConfigManagerImpl`** — `getConfigs(...)` always calls the panel's create-or-attach (never decides from DB links what is missing), then overwrites the DB links with what the panel returns. Builds one `PanelServiceImpl` per configured country of `PanelConfig.COUNTRIES` (`availableCountries()` drives the country buttons). Dispatches to the correct panel based on `country` param ("latv" / "germ" / "pol"); a country without a panel throws instead of falling back to another country, so a config is never created on the wrong server. Country stored in DB `config.country` column. Requests of one user are serialized (double tap). A first request for a name owned by another user (DB row, or a non-zero foreign `tgId` on the panel) throws `ConfigNameTakenException` and the bot asks for another name: create-or-attach would otherwise hand over someone else's client. `getConfigs(userId)` returns approved configs only and refreshes their links from the panel, falling back to the DB if it is down.

**`MergeInbounds`** (`com.petr.tools.MergeInbounds`) — one-off migration script. Reads `clients/list` (which includes each client's `inboundIds`); for every bot client (`_config` suffix or non-zero `tgId`) attaches the XHTTP inbound if it is in the WS inbound, and the Reality inbound always. Leaves old separate `_xhttp` clients untouched. Idempotent.

**`DbService`** — Facade over `UserDao` + `ConfigDao`. Approval is per country, not per config type: a user has one `config` row per country, and its `status` is `"w"` waiting, `"a"` approved, `"d"` rejected. Any type requested in an approved country (including protocols added later) is attached immediately, with no admin request. `tg_user.wait_accept` only records that the user has an approved config; do not use it to decide access.

**`HibernateSessionFactoryUtil`** — Singleton `SessionFactory`, reads `app.env` to pick `hibernate-prod.properties` or `hibernate-dev.properties`. JDBC credentials injected from env vars.

**`DatabaseMigration`** — Runs Liquibase at startup before polling begins.

### Config name convention

User configs are named `{base}_config` (e.g. `petr_config`). The `_config` suffix is always added by the bot; users/admins provide only the base name.

## Bot UX (inline keyboard flows)

### User flow
1. `/start` → welcome message + **[Получить конфиг]** button
2. **[Получить конфиг]** callback → edits message to country selection keyboard:
   ```
   [ 🇱🇻 Латвия ] [ 🇩🇪 Германия ]
   [  🇵🇱 Польша  ]
   [     Отмена     ]
   ```
   Only countries with a configured panel are shown, two per row (Poland disappears without `POL_PANEL_HOME_URL`).
3. **[🇱🇻 Латвия]** → no type choice (Riga has only WS + Reality) → goes straight to step 5
   **[🇩🇪 Германия]** → shows torrent warning with **[✅ Принимаю условия]** / **[❌ Отмена]**
   **[🇵🇱 Польша]** → no warning; type keyboard if the panel has both WS and XHTTP, otherwise straight to step 5
4. **[Принимаю условия]** → shows config type keyboard: `[ WebSocket ] [ xHTTP ] [ Reality ]`, then `[ Все ]` (a protocol button only if the panel has it). Each button gives exactly the named protocol, «Все» gives all of them. The choice itself is generic (`chooseTypeOrRequest`): it is offered only when the country's panel has both WS and XHTTP
5. Config type chosen:
   - Has valid @username → attempt config creation (edits the message)
   - No valid @username → edits message to prompt text input + **[Отмена]**; state = `awaiting_config_name`
6. User types config base name → bot deletes user's message, edits stored message with result
7. Config pending approval → shows **[Проверить статус]** button
8. **[Проверить статус]** → edits message: shows links if approved, or "ещё ждёт" + button again

### Admin flow
1. `/admin` → sends admin panel message + keyboard:
   ```
   [ Синхронизировать с панелью ]
   [   Список пользователей     ]
   [      Удалить конфиг        ]
   [    Выйти из режима         ]
   ```
2. Every button **edits the same message** — result appears above the buttons
3. **[Удалить конфиг]** → edits message to prompt for config name + **[Отмена]**; state = `admin_delete_state`; stores `message_id` in `deleteMessageId`. Admin types name → bot deletes from panel + DB, resets user status, edits message with result
4. Config request notification to admins includes inline **[Одобрить] [Отклонить]** buttons — a decision removes the buttons and shows the outcome and who decided to **all** admins; a late press only reports that the request is already closed

### Admin commands (text fallback)
`/syncPanel`, `/users`, `/exAdmin` — still work as text commands for convenience.

### State machine
| State | Who | Meaning |
|---|---|---|
| `awaiting_config_name` | user | waiting for user to type config base name |
| `admin_state` | admin | admin panel mode active |
| `admin_delete_state` | admin | waiting for admin to type config name to delete |

## Config approval flow

1. User clicks **[Получить конфиг]** → bot creates one client attached to the requested inbounds (WS and/or XHTTP) under a single UUID/subId, saves to DB (`hasConfig=true`, `config.status="w"`), returns `String[]{}` (empty = pending)
2. Bot edits user message: "ожидает одобрения" + **[Проверить статус]**; sends notification to each admin in `ADMIN_CHATS` with **[Одобрить] [Отклонить]** buttons. A repeated request does not notify again while the request is open
3. Admin clicks **[Одобрить]** → `approveConfig` atomically moves the config from `"w"` to `"a"` (of two simultaneous decisions exactly one applies), bot sends the links to the user and closes the request for all admins
4. Admin clicks **[Отклонить]** → status `"d"`, the user is told and may request again (status returns to `"w"`). The panel client stays: the user never received its links, and it may have existed before the request
5. User clicks **[Проверить статус]** → shows approved configs and says which countries are still waiting or rejected. Approval of one country does not open another; new config types within an approved country need no approval

## Config delete flow

1. Admin clicks **[Удалить конфиг]** → prompts for base name (e.g. `petr`)
2. Bot constructs full name (`petr_config`), calls `ConfigManagerImpl.deleteConfig(configName)`
3. `deleteConfig`: finds the configs in DB by name (one per country), deletes the records, resets user `hasConfig=false`/`waitAccept="w"` if nothing is left, calls panel `deleteClient(email)` for each country
4. `deleteClient(email)` → `POST /panel/api/clients/del/{email}` removes the client from **all** inbounds in one call (no per-inbound handling), then the same for the old `{base}_xhttp` twin

## Panel sync (`/syncPanel`)

Runs for every configured panel; each result line starts with the country code. Reads all clients via `GET /panel/api/clients/list`, iterates records with non-zero `tgId`, and for each fetches `GET /panel/api/clients/links/{email}` to rebuild the WS/xHTTP links (sub link from `subId`). Upserts users and configs in DB. Configs new to the DB become approved; existing ones keep their status, because a pending request already has a client on the panel and sync must not approve it. Clients with `tgId=0` update links of a known `_config` by name; `_xhttp` clients are skipped.

## 3x-ui API notes (client-centric, ≥ v3.2.5)

- **Auth:** send `Authorization: Bearer <api-token>` on every request. `checkAPIAuth` sets `api_authed` for valid Bearer tokens, which also makes the CSRF middleware skip the request. No `/login`, no session cookie, no CSRF token needed. (Browser login `POST /login` is now CSRF-protected and unsuitable for the bot.)
- `HttpClient` forced to HTTP/1.1 (HTTP/2 causes issues with some 3x-ui setups).
- Client endpoints live under `/panel/api/clients/*` and take/return **JSON** (`application/json`):
  - `POST /panel/api/clients/add` — body `{"client":{...}, "inboundIds":[2,5]}` (create one client across several inbounds)
  - `POST /panel/api/clients/{email}/attach` — body `{"inboundIds":[...]}` (attach an existing client to more inbounds)
  - `POST /panel/api/clients/del/{email}` — delete the client from all inbounds
  - `GET /panel/api/clients/get/{email}` — `obj`: `{client, inboundIds, ...}`
  - `GET /panel/api/clients/links/{email}` — `obj`: array of ready-made vless links
  - `GET /panel/api/clients/list` — `obj`: array of `ClientRecord` (`email`, `subId`, `tgId`)
  - `POST /panel/api/clients/bulkAdjust` — body `{"emails":[...],"addDays":0,"addBytes":0,"flow":"xtls-rprx-vision"}` changes only the flow (expiry, traffic, HWID untouched). Do not use `update/{email}` for this: it replaces the whole client, and omitted fields (`enable`, limits) get reset.
- `GET /panel/api/inbounds/list` — still exists; used by `MergeInbounds`.
- **XTLS Vision (`flow`)** is stored per client per inbound (`client_inbounds.flow_override`). Checked against 3x-ui source v3.8.5 and v3.11.0:
  - On `add`, the panel keeps the payload's flow only where Vision is possible and clears it elsewhere: TCP + Reality/TLS, and since v3.11 any transport with VLESS Encryption (Warsaw: all three inbounds), on v3.8.5 also XHTTP with VLESS Encryption. The bot always sends `xtls-rprx-vision`.
  - `attach` takes the flow from the client's existing inbounds (first non-empty), so a client with no Vision anywhere (for example WS-only) gets Reality without it. `PanelServiceImpl` calls `bulkAdjust` when it has just added Reality and the Reality link has no `flow=`.
  - It never sets Vision on a Reality the client already had without flow. Xray rejects a link with an empty flow when the server side has Vision ("rejected since the client flow is empty"), which would break links users imported earlier. Existing clients are switched by hand: panel → Clients → select → Bulk adjust → Flow. Users then need to refresh the subscription.
- **Gone in this version:** `POST /panel/api/inbounds/addClient` and `.../delClientByEmail/{email}` (the old inbound-centric client endpoints).

## CI/CD

GitHub Actions (`.github/workflows/push_workflow.yml`) on push to `master` via self-hosted runner: rebuilds Docker image, waits for health check, verifies DB connectivity (`COUNT(*) FROM tg_user`). The `.env` is written from repository secrets; a missing secret becomes an empty value, so the `POL_*` secrets are optional (Poland stays hidden until `POL_PANEL_HOME_URL` is set). A new env var must be added both to the "Create .env" step and to `.env.example`.
